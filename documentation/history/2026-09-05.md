## Later still: the move fix above didn't actually work — root-caused and fixed properly

User retested (d) and reported it still didn't tag a moved note. The "no pending/changed dance
needed — a moved file's cache is already resolved" reasoning behind the first fix was itself wrong.

Diagnosed by adding temporary logging rather than guessing again — two things learned in the
process, worth remembering for next time:

- `console.log` is rejected by this repo's `no-console` ESLint rule; `console.warn`/`error`/`debug`
  are allowed. Started with `console.debug`, which produced nothing visible — Chrome DevTools (the
  console Obsidian's Electron shell uses) hides `debug`-level output under a "Verbose" filter that
  is **not** enabled by default. Switched to `console.warn`, which is never filtered, and got the
  actual data.
- The logs showed `metadataCache.getFileCache(file)` returning `null` immediately after a move, in
  both directions (folder → root, root → folder) — confirming a moved file's cache is **not**
  reliably available synchronously at the moment `vault.on('rename')` fires, contrary to what the
  first fix assumed. `metadataCache.on('changed')` (the fix that already works for `create`) is
  explicitly documented to never fire for a rename, so it can't be the fallback here.

Redesigned around a single shared `pending: Set<string>` (used by both the `create` and `rename`
paths) and one `tryApply(file)` helper, resolved by whichever of three `metadataCache` events fires
first with a usable cache: `changed` (create path, as before), `resolve` (fires per-file
"sometimes after a file has been indexed" — not guaranteed, but free), and `resolved` (the
guaranteed backstop — fires globally "each time files get modified after the initial load," per
its own doc comment; on each firing, every still-pending path is re-checked via
`vault.getFileByPath`). This also means `resolve`/`resolved` now serve as an extra safety net for
the `create` path too, at no extra cost, in the unlikely event `changed` were ever to lag.

Removed the temporary `console.warn` diagnostic calls once the real logs were captured. Rewrote
`spec/design.md`'s "Moving a note into a configured folder" section and its Mermaid diagrams (both
there and in `documentation/Architecture.md`) to describe the corrected design, including the wrong
first assumption as part of the record rather than quietly erasing it. Updated `spec/tasks.md`
Task 4 to describe both correction rounds. Verified: `bun run tsc`, `bun run lint`, `bun run test`
(81 pass), `bun run build`, `bun run rules:check` all green. Redeployed to the test vault.

## Later still: subfolder inheritance (Task 8, new scope)

User asked for auto-tagging to apply to subfolders too, "all the way down" — a note nested several
levels under a configured folder should pick up that folder's tags even with no rule of its own on
the immediate folder. Before implementing, asked a clarifying question since the two reasonable
readings behave very differently: if both an ancestor and the note's own folder have rules, should
the tags combine, or should the nearest one shadow the rest (like CSS cascading)? User chose
**combine** — every configured folder from the vault root down to the note's own folder
contributes its tags, no level shadowing another.

Implemented as `collectAncestorTags(folder, rules)` in `auto-tag.service.ts`: walks `TFolder.parent`
up to the vault root, collecting each level's rule (if any), reversed to root-first order.
`applyFolderTags` now calls this instead of a single `rules[file.parent.path]` lookup; everything
downstream (dedup against the note's existing tags, no-op on an empty combined list) is unchanged.
`FolderTagRulesService` and the settings shape are untouched — this is purely a read-time lookup
change, not a storage change.

Extended `auto-tag.service.spec.ts`'s `makeFile` helper to build a full ancestor `TFolder` chain
(previously just one parent level) and added cases for: ancestor-only inheritance, combining a
folder's own rule with its ancestor's, a 3-level-deep chain where every level contributes, an
exact-duplicate tag across levels not repeating, and — a regression guard — a sibling branch's rule
still not leaking into an unrelated folder (Req 5.1's independence still holds outside the
ancestor/descendant relationship). Test count: 86 (up from 81).

Updated `spec/requirements.md` (qualified 5.1, added 5.4/5.5), `spec/design.md` (new "Subfolder
inheritance" section, revised "Multiple independent folders" and "Applying tags"),

## Later still: retroactive apply on save (Task 9, new scope)

Added `collectMarkdownFiles`/`applyRuleToExistingNotes`/`RetagHost` to `auto-tag.service.ts`:
walks a folder's `children` recursively, and for every existing markdown note found, reruns the
same `applyFolderTags` used for new notes — deliberately not a "diff the old and new rule and
apply just the delta," since letting `applyFolderTags` recompute each note's own full combined
ancestor tag set is what makes a deeply-nested existing note correctly pick up the just-saved
ancestor rule alongside its own folder's rule, and makes "no duplicate tag" fall out for free
rather than needing separate handling. Wired into `FolderTagModal`'s Save button, called only when
the saved tag list is non-empty — clearing/removing a rule must never touch existing notes' tags,
matching the already-established additive-only invariant.

Extended `auto-tag.service.spec.ts` with a `buildTree` helper (unlike the existing
`makeFolderChain`, this builds real `TFolder.children` arrays, not just an ancestor chain) and six
new tests: direct children tagged, nested-subfolder children tagged, a nested note's own rule
combining with the ancestor rule just saved, an already-fully-tagged note left untouched (asserted
via zero `processFrontMatter` calls, not just an empty write), a non-markdown file ignored, and a
file with an unresolved cache skipped without blocking the rest of the walk. Test count: 92 (up
